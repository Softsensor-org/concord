# Existing Repo Adoption Quickstart

Status: implemented (guide) · Owner: Softsensor · Date: 2026-06-25

## Purpose

This guide shows how to apply Concord to a repository that already exists.

The adoption model is an overlay:

> Keep the repo. Keep its tests. Keep its existing delivery conventions. Add
> Concord as the governance layer for AI-assisted planning, execution, evidence,
> and closeout.

This is different from using `coord-template` as a starter template for a new
project.

Before you present this internally, read the scope statement in
`coord/product/PUBLIC_CLAIMS_POLICY.md`. In short: Concord coordinates the work
that goes through `gov`, reduces collisions for governed actions rather than
eliminating them, records supported lifecycle operations rather than all agent
activity, and gives each ticket repository separation rather than process,
filesystem, network, provider, or secret isolation. Overlaying it onto a repo
does not change what an agent can reach — that stays with your environment and
provider configuration.

## 1. Copy Or Install The Concord Layer

Run the installer from the **parent workspace** that contains the independent
product repositories. Review first, then apply the exact digest:

```bash
npx create-concord . --from-existing --dry-run
npx create-concord . --from-existing --apply-plan <digest-from-plan>
```

The standalone SEA binary is the second transactional channel:

```bash
concord init . --dry-run
concord init . --apply-plan <digest-from-plan>
```

`init.sh` is retired and intentionally absent from release artifacts. Manual
copying is recovery only, not a transactional installer; see `USER_MANUAL.md`.

After the Concord engine is present in the parent workspace, run:

```bash
coord/scripts/coord onboard . --dry-run --json
# Review plan_digest, repo/branch/tier/track/gate decisions and starter proposals.
coord/scripts/coord onboard . --write --approve <plan-digest>
# Optional, only after separately approving the proposed starter backlog:
coord/scripts/coord onboard . --write --approve <plan-digest> --approve-starters
coord/scripts/coord init --dry-run
coord/scripts/coord init
```

The onboard path is read-only by default. Discovery reads only the declared
metadata allowlist, and its preview omits private absolute paths, source excerpts,
remote URLs, raw Git output and secret values. Apply accepts the exact reviewed
digest, writes config/decisions/context/receipt in a rollback-capable transaction,
and files explicitly approved starter items only through governed `proposed`
intake. `coord init` is intended to create missing governance seams without replacing existing files;
verify the installer and target state before relying on that behavior. The
existing-repo overlay embeds this same sanitized onboarding preview in its
reviewed install plan, binds apply to both digests, and restores every declared
onboarding output if a later install phase fails.

## 2. Review The Repo Map

Open:

```text
coord/project.config.js
```

Confirm:

- repo codes match the existing repo layout;
- `integrationBranch` matches the real base branch;
- `testCommand` matches the existing local test command;
- track prefixes match the ticket naming convention;
- `coord/setup.decisions.json` captures the chosen adoption profile, phase,
  governance tier, suggested tracks, suggested gates, detected repo shape, and next steps;
- `coord/onboarding.receipt.json` links the reviewed digest, sanitized inputs,
  approved decisions, written files, and any governed proposed-ticket ids;
- no one has hardcoded local machine paths.

For a multi-repo family, update `coord/product/REPOS.md` as the human-readable
map.

## 3. Run The Readiness Doctor

Run the product-facing adoption scanner:

```bash
coord/scripts/coord onboard . --dry-run
coord/scripts/coord onboard . --dry-run --json
```

This is not the same as governance-state repair:

- `coord/scripts/coord onboard` reports adoption readiness and setup decisions.
- `coord/scripts/gov doctor` reports governance state health.

The readiness report identifies detected repo shape, package managers, tests,
requirement sources, shim state, governance setup, setup decisions generated by
`coord onboard --write`, recommended adoption profile, recommended phase, pilot
blockers, enterprise blockers, and suggested tickets.

## 4. Choose The Adoption Profile

Use the doctor recommendation as a starting point.

| Profile | Use when |
| --- | --- |
| `solo-dev` | one developer, prototype, or early repo |
| `small-team` | several developers or agents share one repo |
| `product-engineering` | product work needs requirements, tests, release evidence |
| `regulated` | URS/SRS, validation, audit, or traceability matters |
| `enterprise` | repo-family rollout or command-center view is planned |
| `production-mcp` | agents observe deployed systems through approved adapters |
| `server-bootstrap` | startup, seed, migration, replay, or backfill work is central |

Profiles set governance posture. Tracks still select the work harness.

## 5. Preserve Existing Tests And Gates

Concord should call the repo's existing tests instead of replacing them.

Example:

```js
// coord/project.config.js
module.exports = {
  repos: {
    B: {
      path: "backend",
      integrationBranch: "main",
      testCommand: "npm test"
    }
  }
};
```

If local gates are the authority, do not add GitHub Actions as a new source of
truth just because Concord is installed. If CI is already part of delivery,
document how local gates and CI relate.

## 6. File The First Governed Ticket

Use a small, low-risk ticket first.

```bash
coord/scripts/gov claim --owner <agent-handle>
coord/scripts/gov file-ticket --repo X --type docs --pri P1 \
  --description "Document the existing repo adoption baseline and first gate."
```

Then add a ticket prompt under:

```text
coord/prompts/tickets/<TICKET-ID>.md
```

Run:

```bash
node coord/board/board.js sync
node coord/board/board.js validate
```

## 7. Execute One Ticket End To End

Start:

```bash
coord/scripts/gov start <TICKET-ID> --owner <agent-handle>
```

Make the smallest useful change and record evidence:

```bash
coord/scripts/gov add-feature-proof <TICKET-ID> --proof-path <path>
coord/scripts/gov add-repo-gate <TICKET-ID> \
  --command "<existing local gate command>" \
  --result pass \
  --note "Existing repo gate passed."
```

Add review cycles and requirement closure, then close locally when there is no
PR:

```bash
coord/scripts/gov submit <TICKET-ID> --pr "local-review (no PR)"
coord/scripts/gov finalize <TICKET-ID> --no-pr \
  --landed "Local reviewed change; existing gate passed." \
  --source-commit no-pr-local
```

## 8. Treat Doctor Findings As Work, Not Noise

Doctor findings should become governed tickets when they matter.

Examples:

- missing shims -> shim drift validator or setup ticket;
- missing requirements -> requirements baseline ticket;
- missing test command -> project config ticket;
- GitHub Actions detected but local gates are authoritative -> docs cleanup;
- enterprise blockers -> enterprise hardening roadmap ticket.

Do not silently fix everything in setup. Setup prepares. Governed tickets decide
and deliver.

## 9. Run Business Discovery Before High-Risk Refactors

For existing repos with unclear business context, run a business-discovery pass
before advising major refactors, domain rewrites, schema changes, or generalized
platform extraction.

The discovery protocol records source-backed facts, business objects, field
rules, workflows, configuration surfaces, contradictions, hypotheses, questions,
and promotion candidates. Code is treated as evidence, not automatically as
intent. Implementation-only findings stay `observed` or `candidate` until an
authoritative source or business owner promotes them.

Use the protocol in [`BUSINESS_DISCOVERY_PROTOCOL.md`](BUSINESS_DISCOVERY_PROTOCOL.md)
and the schema in [`business-discovery.schema.json`](business-discovery.schema.json).

## 10. Pilot Boundary

Pilot-ready means the repo has Concord installed, a profile is selected or
recommended, at least one ticket has completed with evidence, local gates are
clear, and limitations are explicit.

Pilot-ready does not mean SSO, RBAC, KMS/HSM signing, tenant isolation, or
enterprise procurement readiness are implemented. Track those separately.

## 11. Board Branch And Push Access

Governance commits the board (Repo X) and, when you opt in with
`--push-before-closeout` / `--push-after-sync`, pushes that commit directly to
the board branch. Before the first `gov finalize`, confirm the board repo's
remote accepts a direct, non-force push to that branch from the identity the
agents use. An org ruleset that requires a pull request on the default branch
(or on `main`, `master`, `production`, ...) refuses that push, and renaming the
branch does not help while it is still the default branch.

`coord onboard` and `gov doctor` check this for you: they read the remote's
effective rules for the board branch (`gh api
repos/<owner>/<repo>/rules/branches/<branch>` plus classic branch protection)
and print a `[board-push]` finding when a direct push would be refused. When
`gh` is missing, not authenticated or offline the finding says `UNKNOWN`; that
is not a pass, so re-run `gov doctor` once `gh` can reach GitHub. Use
`gov doctor --offline` (or `COORD_DOCTOR_OFFLINE=1`) to skip the network check;
it then reports `UNKNOWN (skipped)`.

Pick one option:

- **Exclude the board repo from the ruleset.** Simplest when the ruleset
  exists for product code, not governance state.
- **Add a bypass actor in "Always" mode.** A GitHub App or deploy key that
  the governed push uses, with bypass mode `Always`. A "pull request only"
  bypass does not allow a direct push.
- **Use PR landing mode.** Set `boardLanding: "pr"` in
  `coord/project.config.js` (companion ticket COORD-894) so finalize/land
  opens a governance-only PR for the board commit and enables auto-merge
  instead of pushing. Closeout completes only after that PR merges (with a
  merge commit, not squash or rebase); if it is still waiting on reviews or
  checks, re-run the same terminal verb once it has merged (the open PR is
  reused; set `boardLandingWaitSeconds` to change how long finalize waits).
  The `--push-after-sync` sync commit goes through the same PR path.
- **Configure a different board branch.** Set `boardBranch` in
  `coord/project.config.js` to a branch the ruleset does not cover. A
  non-default branch escapes "default branch" rules, but GitHub still shows
  the old default branch, which then goes stale: people browsing the repo see
  an out-of-date board unless you also change the default branch (which brings
  the rules back) or mark the old branch as not authoritative.

`boardBranch` lives in the project-owned config, so `coord upgrade` keeps it.

## 12. Running Tickets In Parallel

Concord does not limit a repo to one ticket at a time. Its limits apply per
**owner**. A workspace that runs everything as one owner therefore works one
ticket at a time.

**What an owner is.** An owner is a registered agent **handle**: a provider
prefix plus a short id, such as `claudea42` or `codexa00`.

- Handles are recorded in `coord/.runtime/agents.json` with their provider
  (anthropic, openai, google or xai). `gov agentid --assign` creates a new one,
  and `gov claim --owner <handle>` binds the current session to an existing one.
- A ticket's owner is the handle in its board `Owner` field. `gov start` sets it
  from the bound session, and a ticket nobody has started shows `unassigned`.
- From then on, only that owner can change the ticket.

Three related terms are not the owner:

- **A session** is one running agent process, such as a Claude conversation or a
  terminal. Many sessions can act as the same owner over time, for example after
  a restart, but only one at a time holds the owner's lease.
- **The human sponsor** is recorded alongside the owner for attribution. A human
  directs the work, approves overrides and merges, and can contribute reviews,
  but a governed ticket is still owned by exactly one agent handle at a time.
- **Moving a ticket to another owner** is an explicit, journaled step: same-owner
  restarts use `gov resume <ticket>`, and a transfer to another handle uses
  `gov claim <ticket> --transfer-to <handle> --human-admin-override "<reason>"`.

The limits:

| Limit | Where it is enforced | Way around it |
|---|---|---|
| Unrelated `doing` tickets held by one owner are reported, not refused. Tickets in `review` do not count. | `gov doctor` warning `[owner-doing]` | Finish or reassign one, or record a closeout-blocker relation (below) for a pair that closes together |
| One live session per owner lease, expiring 15 minutes after the session goes quiet (`COORD_INSTANCE_TTL`) | Every governed mutation | One handle per agent |
| No hard limit on total `doing` tickets (the former 5-ticket WIP limit was documented, not engine-enforced; retired with the owner cap, COORD-963) | Orchestrator review | Not applicable |
| One fresh writer per worktree | Co-located-writer guard (COORD-224) | A separate worktree per ticket. `--allow-shared-worktree` is an orchestrator-only exception. |

Why the limits exist:

- **Attribution.** Every change in the hash-chained journal belongs to exactly
  one owner and session. Two writers under one identity make the record
  ambiguous.
- **No silent overwrite.** A single lease means a crashed or stale session
  cannot overwrite a live one. A takeover over a live session needs
  `--human-admin-override`.
- **Reviewable work in progress.** The board-wide cap keeps unreviewed work small
  enough for a human to review.
- **Hooks cannot authenticate the acting sub-agent.** Every sub-agent in one
  Claude conversation shares one `CLAUDE_CODE_SESSION_ID`, so a hook cannot
  enforce per-sub-agent ownership inside a worktree (COORD-648). Governance stays
  conservative instead.

How to run work in parallel:

1. **One handle per agent.** Give each agent its own session identity and handle
   before it runs any `gov` command, then have it start its own ticket:

   ```sh
   export COORD_SESSION_ID=<unique-per-agent>
   coord/scripts/gov agentid --assign            # or: gov claim --owner <handle>
   coord/scripts/gov start <ticket> --owner <handle>
   ```

   Each ticket gets its own worktree, so agents on the same repo do not collide.
   `coord/engine/docs/MULTI_AGENT_TOPOLOGIES.md` has the full matrix.
2. **Separate conversations or terminals for Claude.** In one Claude
   conversation, sub-agents share the harness session id. A distinct
   `COORD_SESSION_ID` per sub-agent is mandatory there, and separate sessions
   avoid the problem entirely.
3. **Submit, then start the next ticket.** A ticket in `review` frees its owner,
   so one agent can keep several tickets moving through review.
4. **Same-owner exception.** When a second ticket blocks the closeout of the one
   in `doing`, record the relation and the owner may hold both:
   `coord/scripts/gov set-followup-relation <new> --depends-on <doing> --relation closeout-blocker`.
5. **Prepare in isolation, land serially.** Agents without `gov` access can
   prepare changes in separate clones. One owner then lands them in order, with
   gates. This gives parallel development without parallel board writes.

These always stay serial: board mutations (they take the board lock), landing
of stacked tickets (each starts from the base the previous merge produced), and
any gate that the host's memory cannot run twice at once.

### Sub-agents, parallel preparation and one integrator

`coord/engine/docs/MULTI_AGENT_TOPOLOGIES.md` defines two topologies, independent
sessions or one orchestrator with sub-agents, and the rule that workers implement
locally and the orchestrator publishes. Three points are easy to miss.

**Identity support is provider-specific; check both halves.** A distinct
`COORD_SESSION_ID` fixes how the `gov` CLI identifies a worker. It does not prove
that the file-edit hooks recognize that worker.

- Claude sub-agents in one conversation share one `CLAUDE_CODE_SESSION_ID`, and the
  write hook attributes every edit to the conversation's handle (COORD-648). They
  can run `gov` verbs and read, but cannot edit their own ticket worktree under
  their own handle.
- Before calling a topology supported for parallel implementation with a given
  provider, verify both CLI identity and hook attribution.

**Parallel preparation with one governed integrator is a distinct mode, with
its own contract.** It is not fully governed parallel implementation, and the
publication rule does not waive ownership.

- *Authority.* Reserve the ticket on the shared board before any preparation
  starts: the integrator claims it, or the worker does under its own handle.
  Never prepare an unreserved ticket. Separate clones prevent file collisions,
  not duplicate implementation.
- *Handoff.* The worker returns:
  - the exact commits (SHA and tree id) and the base commit;
  - the files touched;
  - the targeted test commands, with results on each required runtime;
  - any new test titles, and whether they are registered;
  - open questions.
- *Attribution.* Worker commits carry a trailer naming the worker. The integrator
  records the worker and the handed-off SHAs in the ticket's plan evidence.
- *Integration.* The integrator applies exactly those commits in the ticket
  worktree, and confirms the code tree matches the handed-off tree.
- *Publication and landing.* Only the integrator pushes, opens the PR, merges
  after approval, and closes the ticket.

**Where verification runs is a scheduling choice, but it is never skipped.**

- Workers may run targeted tests and leave full gates to the integrator, which is
  sensible on a shared or small host.
- The final integrated tree must still pass every required check.
- If the integrated tree differs from the tree the evidence was produced on,
  that evidence does not count.

**Teams on different machines** need a shared reservation, not just separate
clones. Reserve and publish ticket records on the shared board before either
side starts. Atomic remote claims are tracked as COORD-899.

## 13. Test And Gate Practices

These come from gating real multi-ticket stacks on laptops and on large hosts.

- **Bind evidence to a tree, not a branch.** Record the commit and tree id you
  gated, plus every setting that differed between attempts (for example a raised
  `GOVERNANCE_SUITE_TIMEOUT_SECONDS`). A machine-readable run manifest is
  tracked as COORD-910.
- **Qualify stacked evidence.** A pass on the top of a stack does not prove that
  each intermediate commit passes. Reuse top-of-stack evidence for the tickets
  below it only under an explicit, recorded batching decision. Re-validate if
  landing changes the tested tree or its base.
- **Classify a failure before filing it.** Reproduce it on the base tree, on the
  branch, and in a clean clone. Load, memory reaping and disk stalls often look
  like regressions.
- **Treat gate capacity as a shared resource.** Do not run a full gate next to
  other heavy test jobs on the same machine. Use a dedicated gate host when you
  have one. Serial runs remain the authority (COORD-900 tracks opt-in sharding
  for large hosts).
- **Keep test environments clean, but not empty.** Remove agent and session
  identity from test subprocesses. Keep the credentials, proxy settings and
  toolchain paths they need. The governance process keeps its own identity to
  record the result (COORD-909 audits product-repo gates).
- **Check host prerequisites up front.** Check the git version (COORD-902), the
  umask (COORD-901), and whether the temp directory is under `/tmp` and not
  behind a symlink (COORD-903). Each of these has cost a full gate attempt.
- **Use progress timeouts with hard ceilings.** A progress timeout separates a
  stall from slow work; a hard upper bound stops a runaway (COORD-896).
- **Register new tests as you write them.** Add every new test title to
  `release/suite-inventory.json` for both editions in the same change. Do not
  wait for the release check to catch it (COORD-906).
- **Use targeted coverage as an early warning only.** Run coverage on the changed
  suites before the full gate to catch newly exposed branches early (COORD-907).
  The whole-suite ratchet stays the gate.
- **Recover from killed runs safely.** A crash or out-of-memory kill can leave
  lock staging folders and child processes behind. Clean them up only when you
  can prove the dead run owned them (COORD-905).

- [ ] Adoption profile chosen or accepted from doctor.
- [ ] Existing test commands preserved.
- [ ] Agent shims point to `coord/GOVERNANCE.md`.
- [ ] First ticket prompt added.
- [ ] First governed ticket completed.
- [ ] Business discovery run planned for high-risk existing-repo changes.
- [ ] Pilot blockers and enterprise blockers separated.
