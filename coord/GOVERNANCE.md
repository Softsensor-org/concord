# Governance Policy

This is the canonical execution policy for a project using this coordination scaffold.

Version: v0.5.0 (2026-05-16)

Layer label: `current-enforced-policy`

Use this file for:
- enforced governance rules
- canonical file ownership
- authority order and lifecycle constraints

If another governance doc conflicts with this file on an active rule, this file wins.

## 1) Goals

This governance is optimized for:
- safe parallel work across governed repos and `coord`
- one canonical board
- deterministic ticket state
- low-friction startup for new agents

## 3) Engine and project filesystem boundary

Reusable governance implementation is being established under `coord/engine/`.
New engine-canonical files land there from creation and are upgraded as one
template-managed unit. During the COORD-514..516 migration, engine-relative
module requests resolve through `coord/paths.js`: `coord/engine/<path>` is
accepted when present, the legacy `coord/<path>` is accepted as a compatibility
fallback, and simultaneous copies fail closed with both paths named. Project
configuration and state remain outside the engine tree and are supplied through
the validated config seam in ADR 0013. No engine module may infer project paths
by walking parent directories or by reading arbitrary project-owned files.

## 3) Authority Order

When instructions conflict, use this order:
1. Human-admin
2. `coord/GOVERNANCE.md`
3. Ticket prompt in `coord/prompts/`
4. Repo-local `AGENTS.md` files
5. Tool-specific shim files (`CLAUDE.md`, `CODEX.md`, `GEMINI.md`)
6. Orchestrator cycle decisions
7. Agent judgment

Rules:
- Orchestrator decisions cannot override human-admin instructions, governance, or ticket prompts.
- If an orchestrator instruction conflicts with a higher authority, stop and log the conflict in `coord/QUESTIONS.md`.

## 3.1) Agent Entry Paths

This governance is agent-agnostic. Use `coord/AGENT_PATHS.md` as the single practical guide for Codex, Claude, and Gemini native entry flows.
All governed mutations still converge through the shared CLI or MCP core regardless of which frontend or wrapper path an agent uses.

Rules:
- the preferred operator surface is the small facade defined in `coord/VERB_CONTRACT.md` and implemented at `coord/scripts/agent`
- this policy references `coord/VERB_CONTRACT.md` for the canonical facade verb list instead of restating that list here
- `coord/scripts/agent` is a thin adapter over the existing governance core; it must not duplicate lifecycle logic from `coord/scripts/gov` or the MCP layer
- raw `coord/scripts/gov` remains the admin, CI, break-glass, and deep-inspection surface
- Choose one native path per session.
- Cross-agent handoffs are allowed only through clean `claim` / `resume` semantics.
- Tool-specific wrappers do not override governance, ticket prompts, or board state.
- comparative-strength routing across Claude, Codex, and Gemini should use `coord/AGENT_CAPABILITY_REGISTRY.md`, not prompt folklore

## 3.2) Agent Boot, Retrieval, and Externalization Contract

This section defines the cold-start contract for every governed agent. It adds no
new subsystem: agents resume from existing governed artifacts and write durable
learning back into those same artifacts.

Chat memory is non-authoritative. A transcript, model memory, or remembered
prior answer may help locate relevant material, but it never outranks the board,
governance journal, plan records, prompts, repo gates, feature proofs, accepted
ADRs, or product requirement sources.

Boot sequence:
1. Read the thin entry shim: root `AGENTS.md`, then the active tool shim
   (`CODEX.md`, `CLAUDE.md`, or `GEMINI.md`) when present.
2. Resolve canonical precedence from this file, then the ticket prompt,
   repo-local `AGENTS.md` files, tool shim, orchestrator cycle decision, and
   agent judgment in the authority order above.
3. Bind identity before mutation. Use `coord/scripts/gov agentid --assign` for a
   fresh session, then `start`, `claim`, or `resume` the ticket through
   governance as appropriate for the current state.
4. Retrieve the minimum governed context before planning.
5. Plan, execute, verify, and move through the review gate.
6. Externalize durable learning before closeout so the next cold-start agent can
   resume without relying on chat memory.

Minimum context for nontrivial tickets:
- `coord/scripts/gov explain <ticket>` as the first ticket read;
- the ticket prompt or waiver and current board row;
- the active plan record, prework/context-pack, and ticket-local notes when they
  exist;
- relevant recall or memory-claim proposals, treated as leads until verified
  against governed artifacts;
- accepted ADR references, ADR proposals linked from the ticket, and product
  requirement sources that the ticket cites or modifies;
- business-discovery packs or requirements packs for discovery/product-shaping
  work;
- repo-local `AGENTS.md` files and gate docs for every repo touched by the
  declared write scope.

Externalization requirements:
- record plan updates, requirement-closure evidence, review cycles, feature
  proofs, and repo-gate results through governance where the CLI supports them;
- link accepted ADRs or record an ADR proposal when the work changes durable
  architecture, coordination semantics, or operator policy;
- record memory-claim proposals only for reusable learning that has been
  verified against current governed artifacts;
- resolve questions, decisions, and reflections in the appropriate governed
  logs instead of leaving them only in chat;
- close out with enough evidence that a new agent tomorrow can run
  `coord/scripts/gov explain <ticket>`, read the linked artifacts, and understand
  what was done, what remains deferred, and which gates proved it.

## 4) Ticket Status Model

### Legal statuses

- `todo`
- `doing`
- `doing (blocked: <reason>)`
- `review`
- `done`
- `deferred`
- `superseded`

### Legal transitions

```text
todo -> doing
doing -> review
doing -> doing (blocked: <reason>)
doing (blocked: <reason>) -> doing
review -> done
review -> doing
todo -> deferred
deferred -> todo
any -> superseded
```

Guarded wrong-start exception:
- `doing -> todo` is allowed only through `gov unstart <ticket-id>`
- `gov unstart` is same-owner only and must fail closed once the ticket has accrued review, landing, plan, or workspace evidence that should remain auditable on the board
- foreign stale-state cleanup remains an explicit admin path (`lock-abandon`, `claim <ticket-id> --transfer-to <handle> --human-admin-override "<reason>"` for an ownership transfer, or orchestrator cleanup with human-admin override)

## 5) Ownership and Locks

- Only one active owner per `doing` ticket.
- Code-edit tickets require a lock at `coord/.runtime/locks/<ticket>.lock`.
- Lock files must include (v2 owner-authoritative model — see §10.3):
  - `owner`
  - `ticket`
  - `status`
  - `repo` (configured repo path from `coord/project.config.js`, or `coord`)
  - `branch`
  - `worktree`
  - `started_at_utc`
  - `heartbeat_utc`
  - `head`
  - `identity_model` (`"v2"` on locks written under the durable identity
    channel; authority is the **owner lease**, not a session token)
- **Legacy fields** `session_id` / `thread_id` are no longer authority.
  They remain readable on pre-v2 locks for ≥1 release (ignored for
  authority, `gov doctor`-warned) and MUST NOT be written as authority on
  new v2 locks. GCV-1 removes no code; deletion of the legacy
  session/thread machinery is a later, fleet-migration-gated release.
- this section defines the high-level required lock fields only; `coord/engine/docs/AGENT_ID_COLLISION_RECOVERY_POLICY.md` Section 3 and Section 5.4 are the normative source for the full lock schema semantics, including complete-lock validation and `head` meaning
- for coord-owned tickets, when ADR-0008 resolves a control-plane Git repository, `head` is the governed worktree commit anchor and must match that worktree's `HEAD` when it is on its canonical branch; only a topology with no control-plane Git repository uses `coord-no-git-head`
- for product-repo tickets, `head` is the governed worktree commit anchor and should match that worktree's `HEAD` when the worktree is on its canonical branch
- a no-repository sentinel is not a way to suppress drift for an existing control-plane worktree; read-only `gov doctor` reports stale values and `gov recover <ticket>` refreshes a legacy sentinel after ownership and registered-worktree checks
- `doing` tickets must have a valid lock.
- Non-`doing` tickets must not have a lock.

## 6) Repo Codes

Repo codes are defined in `coord/project.config.js`. Each code is a single uppercase letter mapping to a repo directory. `X` is always reserved for coord/cross-repo work.

Default project config:
- `B` = first repo (default: `backend`)
- `F` = second repo (default: `frontend`)
- `X` = cross-repo, design, planning, or coord-owned work

Additional codes can be added for projects with more repos (e.g., `M` = mobile, `W` = worker). The governance CLI, board validator, and MCP server read project config through `coord/paths.js`; edit `coord/project.config.js`, not engine-managed `paths.js`.

## 7) Worktree Rules

- Fleet mode is worktree-per-agent by default. Every governed agent must work from a repo-local or coord-owned worktree under `.worktrees/<agent>/<ticket>/`; a shared checkout/runtime is not a supported multi-agent execution surface.
- `gov start` provisions the ticket worktree automatically. Repo-backed tickets use the product repo's `.worktrees/<agent>/<ticket>/`, kept out of the product clone's status through its clone-local `.git/info/exclude`, never its tracked `.gitignore` (COORD-892, `coord/DIRECTORY.md`); repo `X` tickets use a real coord git worktree under `coord/.worktrees/<agent>/<ticket>/` with a worktree-local `coord/.runtime/` scaffold. Journal and plan records are tracked durable evidence; locks, sessions and recovery snapshots stay gitignored as specified in `coord/DIRECTORY.md`.
- A second heartbeat-fresh governed session in the same checkout/runtime is refused by default. Use a separate git worktree with its own `coord/.runtime`; pass `--allow-shared-worktree` only for deliberate single-agent/local or orchestrator-controlled exceptions where the operator accepts the shared-runtime risk.
- Repo `X` work is split by declared file surface:
  - safe coord code/doc surfaces such as `coord/scripts/`, `coord/docs/`, `coord/product/`, `coord/ui/`, `coord/GOVERNANCE.md`, and repo-local agent guide files may be scheduled in parallel waves when declared files are disjoint;
  - global coordination state such as `coord/board/`, `coord/.runtime/`, `coord/.worktrees/`, `coord/prompts/`, `coord/rendered/`, `coord/PLAN.md`, and `coord/QUESTIONS.md` remains single-writer and must be scheduled alone.
- Repo `X` tickets without declared files are treated as potentially global-state-affecting and scheduled alone.
- The repo root should stay clean.
- Never overwrite another agent's work.
- If unrelated dirty files are found, stop and log the conflict in `coord/QUESTIONS.md`.

## 7.1) Branch Promotion Model

For governed repo work (any repo code except `X`):
- ticket branches land on `dev`; `dev` is the canonical integration branch for landing evidence, ancestry audit and feature-proof checks
- no-PR and PR-backed ticket closeout records landing evidence against `dev` unless a human-admin explicitly overrides the base branch
- promoted branches, in order: `staging`, then `main`; release donor branches `concord-public-release` (Community) and `concord-enterprise-release` (Enterprise) are fed only from `main`
- allowed promotion edges are only `dev -> staging`, `staging -> main`, `main -> concord-public-release`, and `main -> concord-enterprise-release`; any other edge is refused
- the gate for each edge is: PRs into `dev` run the impact radius on Node 22; `dev -> staging` runs the full suite sharded on Node 22; `staging -> main` runs the full suite on Node 22 and Node 24 plus the coverage ratchet; `main -> concord-public-release` runs the public release gates; `main -> concord-enterprise-release` runs the Enterprise cut build and Enterprise qualification
- every promotion is a fast-forward of an exact commit that passed the gate for its edge; promotions create no merge commits and no forced pushes
- promotion goes only through the governed promotion verb, by the integration authority (GOVERNANCE 11.0); release edges also require explicit human-admin approval for that commit and edition
- release donor branches record the donor commit, cut tree digest and manifests of each released edition (see ADR 0028)
- no agent pushes to `main`, `staging`, `concord-public-release` or `concord-enterprise-release` directly; promoted-branch rulesets will enforce this once those branches are created (separate human-admin approval)
- `main` is not advanced as part of ticket closeout; it moves only by promotion after the relevant `dev` baseline has landed and stabilised

## 7.2) Git Management

For governed repo work (any repo code except `X`):
- `gov start` is the earliest git safety gate; if `origin` is configured, refresh `origin/<base>` before creating a new governed branch
- `--offline` is the explicit escape hatch for start-time branch creation when network refresh is unavailable or intentionally skipped; in offline mode, governance may rely on locally cached refs
- local preflight must fail closed on detached HEAD and on direct work from `dev` or `main`
- commit subjects must already contain the ticket ID; governance validates this but does not rewrite the subject automatically
- targeted staging is the default expectation for governed commits; broad staging is only allowed through an explicit override (`--all`)

Merge-method policy:
- default to `squash` for ordinary ticket landing
- use `rebase` only when the repo or hosting policy requires linear history and the ticket branch is intentionally reviewable as a small linear series
- use `merge` only by explicit exception when preserving branch topology or multi-commit ancestry is itself part of the reviewed change

## 8) Start Gate

Before moving a ticket to `doing`:
1. Read `coord/AGENT_STARTUP_CHECKLIST.md`.
2. Confirm the ticket exists in `coord/board/tasks.json`.
3. Confirm the status transition is legal.
4. Confirm there is a prompt mapping in `prompt_index` whose content satisfies the prompt content contract (see Prompt Content below), or an explicit waiver in `waiver_index`.
5. Verify the ticket prompt's declared preconditions against the target repo's integration branch (see Prompt Preconditions below).
6. Bootstrap or materialize canonical plan state.
7. Auto-seed startup / traceability attestation at start time.
8. If the ticket type is `test`, `contract`, or `infra`, record baseline reproduction before the start can complete. `Command:` and `Outcome:` entries must carry nonblank values; where no baseline can exist, record an explicit `Not-required: <reason>` entry instead.
9. Acquire the lock and create the governed workspace.
10. For repo-backed tickets, refresh `origin/<base>` before creating a new branch when `origin` is configured; use `--offline` only as an explicit local-ref fallback, then print reproducible dependency bootstrap guidance.
11. Run `coord/scripts/gov sync`.

### Prompt Preconditions

A ticket prompt may declare an OPTIONAL `## Preconditions` section listing concrete artifacts the ticket claims **already exist** and will modify or gate — for example a security ticket gating an existing route, or a refactor ticket changing an existing symbol. The start gate parses that section and verifies each declared artifact against the target repo's integration branch (`origin/<base>`, falling back to a local `<base>` branch) using cheap git lookups only — no build, no checkout:

- a file path is verified with `git cat-file -e <ref>:<path>`
- a route or text literal is verified with `git grep` against the integration ref
- a `symbol:<path>#<literal>` entry requires both the file and the literal

If any declared precondition does not resolve, the start gate fails **before** any lock or worktree is created, with a clear stale-prompt error naming the unresolved artifact(s). This catches prompts authored ahead of a dependency that has not landed.

Rules:
- The section is optional. A prompt with **no** `## Preconditions` section declares nothing, verifies nothing, and starts normally — existing prompts are unaffected.
- Each precondition is a path / route / symbol. Use the explicit `path:` / `route:` / `text:` / `symbol:<file>#<literal>` prefix form, or a bare token (a leading `/` is treated as a route literal; a path-shaped token is treated as a file path).
- `## Likely Files` are NOT preconditions and never block a start — those are frequently files the ticket will create.
- Declare an artifact as a precondition only when the ticket premise is false without it.

### Prompt Content

Prompt coverage is a content contract, not file presence. Unless a prompt waiver is recorded, `gov start` reads the mapped prompt (or the on-disk `coord/prompts/tickets/<ticket-id>.md` it would auto-register) and fails, naming the ticket, the prompt path, and each reason, when:

- the file is missing, not a regular file, unreadable, not valid UTF-8 text, or empty
- a ticket-specific prompt has no `## Acceptance...` heading at all
- an `## Acceptance...` section holds no ticket-specific criteria — only the generated scaffold lines ("Ticket scope is implemented.", "Focused verification is recorded in the governed plan."), `TODO` placeholders, or nothing
- an `## Acceptance...` or `## Verification` section still carries a `TODO` placeholder line

Rules:
- `gov file-ticket --with-prompt`, `gov open-followup` / `gov split-ticket`, and `gov register-prompt --create` lift the ticket's own acceptance text from its board Description into `## Acceptance Criteria` (and verification text into `## Verification`). Recognised forms: an `Acceptance:` / `**Acceptance:**` / `Acceptance criteria:` label (the text runs to the next blank line or `**Label:**`) or an `Acceptance` markdown heading. A ticket filed with acceptance text is start-ready in one step; without it the generated `## Acceptance Criteria` holds a `TODO` that names what to add, so `gov start` refuses it until the criteria are authored with `coord/scripts/gov register-prompt <ticket-id> --body-file <file>`. When the Description has no verification text, the generated `## Verification` directs the focused verification commands and results into the governed plan, where the closeout gates enforce them.
- The validation is deterministic and structural: it checks presence and placeholders, not whether the criteria are semantically adequate. Reviewers still own adequacy.
- `gov explain` start readiness reports exactly the refusal `gov start` would raise (same `prompt_coverage` code and message).
- `## Likely Files` and `## Preconditions` remain optional; a `TODO` stub under `## Likely Files` never blocks a start.
- Ticket-specific versus shared role prompt (human-admin ruling, 2026-10-14): a prompt is a shared role prompt only when its resolved path is on an explicit allowlist: the role prompts the engine ships in `coord/prompts/` (`implementer.md`, `planner.md`, `reviewer.md`) and the workspace-relative paths a project lists in `coord/project.config.js` under `promptCoverage.rolePrompts` (an entry with a `..` segment or outside the workspace root is ignored). Directory placement and the number of tickets mapping a file confer nothing, and a ticket's own `coord/prompts/tickets/<ticket-id>.md` or any path under the ticket prompts directory is never a shared role prompt, even if listed. Every other prompt — the ticket's own file (mapped, or on disk and about to be auto-registered), another ticket's prompt, and any other path — is ticket-specific and must carry an `## Acceptance...` heading; without one `gov start` refuses it with the same attribution as the other content failures, and the recorded `prompt_coverage` waiver is the only bypass. A shared role prompt with no acceptance heading is not judged for acceptance content; one that does declare an acceptance heading is judged like any other.
- The contract is evaluated at start only. Prompts of tickets already in `doing`, `review`, or a closed status are not re-evaluated.
- A recorded prompt waiver is the only bypass.

### Prompt Waivers

When a ticket does not have a prompt mapping in `prompt_index`, it must have an explicit waiver in `waiver_index` before it can move to `doing`. Waivers are recorded in `coord/board/tasks.json` and must include:
- `code`: the waiver type (currently `prompt_coverage`)
- `reason`: why a prompt is not required
- `recorded_at`: when the waiver was recorded
- `recorded_by`: who recorded it

Prompt creation and registration:
- low-ceremony `gov file-ticket` remains valid without prompt coverage
- when a ticket should carry a registered prompt at creation time, use
  `coord/scripts/gov file-ticket ... --with-prompt` to create
  `coord/prompts/tickets/<ticket-id>.md` and register `prompt_index` coverage
  in the same governed mutation; the prompt is start-ready when the
  Description carries acceptance text (see Prompt Content)
- when an existing ticket needs its missing canonical prompt, use
  `coord/scripts/gov register-prompt <ticket-id> --create`
- do not hand-create prompt files and then repair sealed-state drift unless
  explicitly recovering from an interrupted command; the governed create/register
  path is the normal atomic path
- a ticket already registered to a different prompt path must fail closed unless
  the operator passes an explicit replacement/force flag

## 9) Review Gate

Before moving `doing -> review`:
- run the relevant repo checks defined by `coord/product/TESTING_AND_GATES.md` and `coord/product/LOCAL_AUTOMATION_AND_GATES.md`
- record verification commands in the plan record / plan ledger
- record explicit requirement-closure evidence in the plan record:
  - `Ticket ask: ...`
  - `Implemented: ...`
  - `Not implemented: ...`
  - `Deferred to: <ticket-id or none>`
  - `Closeout verdict: complete`
- for governed code-repo tickets at or after the feature-proof cutoff, record canonical `Feature proof` entries in the plan record:
  - `path:<repo-relative-file>`
  - `symbol:<repo-relative-file>#<literal-or-symbol>`
  - `text:<literal>`
  - `route:<literal>`
- perform at least 4 self-review cycles for substantive code-repo changes, covering:
  - contract/state invariants
  - auth/security/failure modes
  - tests/operability/performance
  - requirement closure
- `coord`-only governance changes still require at least 3 structured self-review cycles
- if a governed code-repo ticket was merged to the canonical base branch before `doing -> review`, treat that as a sequence violation:
  - do not use `supersede`
  - do not hand-edit board state
  - repair it with `coord/scripts/gov finalize <ticket-id> --no-pr --already-landed --landed "<canonical-branch closeout proof>"`
- release the lock in the same cycle
- sync the board

## 10) Done Gate

Before moving `review -> done`:
- confirm merge / closeout evidence
- record the canonical landed commit, and record the source commit too when it is still available
- when a ticket is satisfied by later work, record that explicitly via `fulfilled_by_ticket` and/or `fulfilled_by_commit_sha` instead of relying on narrative notes
- confirm the landed commit is recorded and is an ancestor of the canonical base branch (`dev` unless explicitly overridden)
- run any required canonical feature-proof audit for governed code-repo tickets
- remove the governed worktree for code-repo tickets
- keep any follow-up work in a new ticket; do not reopen `done` tickets
- when a repo has a configured remote, prefer PR-backed landing; use no-PR closeout only as an explicit exception
- do not advance `main` during ordinary ticket closeout; promote `dev -> main` only as an explicit post-landing action
- `supersede` is only for obsolete work that is not already landed on the canonical base branch; landed work must close through the governed review/done path
- sync the board

## 10.1) PR Merge Conflict Resolution

If a PR cannot merge due to conflicts:
- the owning agent must rebase the ticket branch against the current base ref (`dev`)
- verify no new test failures are introduced by the rebase
- force-push the rebased branch with `git push --force-with-lease`
- confirm the PR merge state returns to `MERGEABLE` before retrying `gov land`
- do not use the `--admin` flag to force-merge over conflicts

If a base ref has diverged significantly or the branch is stale:
- consider opening a new PR from a fresh branch
- supersede the conflicted ticket only if the underlying work is obsolete

## 10.2) Revert and Hotfix Policy

- reverting landed work requires a new governed ticket; do not reopen or rewrite the historical ticket that originally landed
- ordinary urgent fixes land on `dev` first, through the ticket path, then move through `staging` and `main` under the normal edges (ADR 0028 section 6)
- a release-only fix is still made on `dev`; it promotes through `staging` and `main`, and the next release edge carries it
- a direct `main` hotfix is human-admin only (ADR 0028 section 6): it records the override reason explicitly and opens a follow-back ticket that replays or verifies the fix on `dev` before the next promotion
- a hotfix never goes directly to a release branch (`concord-public-release` or `concord-enterprise-release`)
- a direct `main` hotfix does not count as restoring normal branch alignment until the follow-back work is landed on `dev`

## 10.3) Identity and the Owner Lease (v2)

> **Rewritten for GCV-1 (identity v2).** This supersedes the prior
> tty-fingerprint / "one live conversation per board" / explicit-
> `CLAUDE_SESSION_ID` rule. That rule existed *because* "a provider [had
> not yet exported] a stable per-conversation child-process identity."
> That premise no longer holds: Claude Code's `SessionStart` →
> `CLAUDE_ENV_FILE` channel is the durable, explicit per-conversation
> primitive that was missing. The reversal is justified by the primitive
> becoming available — exclusivity is **strengthened** (an owner lease),
> not relaxed.

**Core invariant.** A ticket may be mutated only by its recorded `owner`,
through exactly **one fresh live instance** holding that owner's lease.

- **Durable identity** comes from the provider session
  (`COORD_PROVIDER_SESSION_ID`, from the Claude `SessionStart` hook via
  `CLAUDE_ENV_FILE`). **Live exclusivity** is a per-attach
  `COORD_INSTANCE_ID`. `provider_session_id`, `transcript_path`, pid/host
  are **evidence/diagnostics only — never authority**.
- **The mutex is the owner lease**, not a session token: at most one live
  registered instance per `owner`, regardless of how many provider
  sessions exist.
- **Liveness** is heartbeat + TTL (default 15m, `COORD_INSTANCE_TTL`).
  Stale instances are reapable and never block. **Owner-level
  split-brain** (≥2 fresh instances for one owner) fails closed.
- **Same-owner fast handoff** (crash / fast restart): `gov claim --owner
  <X> --handoff [--reason <text>]` atomically journals an
  `owner-lease-handoff`, transfers the lease, and revokes the prior
  instance (which then fails closed explicitly on its next mutation — no
  silent steal). Same-owner only; a cross-owner change of owner still
  requires `--human-admin-override "<reason>"`. Bare `--force` is a deprecated
  legacy alias only. COORD-893 ruling: while the agent session being
  replaced is still live on another thread, `--handoff` (like `--force`)
  also needs `--human-admin-override "<reason>"`; once that session is
  stale or expired (v2: owner lease past its TTL; legacy: session idle
  past 4h), `--handoff` needs no override.
- **Missing/ambiguous durable channel ⇒ fail closed** with an actionable
  message (explicit-claim-only). Authority is never inferred. MCP mutating
  tools are read-only under v2 (the long-lived server cannot prove
  per-call identity).
- `.runtime/agent_sessions.json` and the v2 instance registry are runtime
  state, not canonical ticket ownership by themselves; when runtime state
  conflicts with a valid governed ticket lock, the ticket lock (owner)
  wins.
- **Migration:** pre-v2 locks with `session_id`/`thread_id` remain
  readable for ≥1 release (ignored for authority, `gov doctor`-warned).
  GCV-1 deletes nothing; removing the legacy session/thread machinery is
  a later release gated on downstream fleet migration + GCV-4.

## 10.8) Governance Drift Classification

`detectGovernanceProvenanceDrift` (in `coord/engine/scripts/journal.js`) compares the governed filesystem snapshot to the last journaled snapshot. The resulting drift paths are split by `splitGovernanceProvenanceDrift` (`coord/engine/scripts/lifecycle-board-commands.js`) into two buckets:

- `warnings` — paths under `coord/.runtime/agent_sessions.json` or `coord/.runtime/session-threads/*`. These churn from session normalization; they do not block and are not logged as a QUESTIONS.md drift-note row.
- `blocking` — every other governed file, **including** `coord/QUESTIONS.md`, `coord/PLAN.md`, and the plan records under `coord/.runtime/plans/*.json`. Pre-existing blocking drift detected at the start of a governed mutation is logged as a drift-note row in `coord/QUESTIONS.md` and surfaced by `gov doctor`.

The mutation records the pre-existing drift in the governance event journal under `details.preexisting_drift` (the drift path list) and `details.preexisting_drift_logged_to_questions` (whether the drift-note row was written), so observability is preserved. To rotate `coord/QUESTIONS.md` before applying this classification to historical rows, follow `coord/engine/docs/QUESTIONS_ROTATION_PROTOCOL.md`.

### Sanctioned writes and reconciliation

`gov sync` may recover an exact deterministic generated projection without a
human override. Under the journal lock it checks the complete snapshot against
its baseline, requires every changed path to be a supported rendered view, and
compares its bytes with a read-only regeneration from unchanged canonical inputs.
The recovery is recorded in the sync event, with old and new digests. Manual
PLAN content, mixed authoritative edits, missing provenance and unsafe file types
remain refused. Rendering policy/configuration/schema inputs are included in new
snapshots; legacy baselines lacking those entries cannot authorize automatic
recovery. A normal journaled engine upgrade establishes the new baseline; an
already-wedged legacy baseline needs the existing reviewed reconciliation path.
Direct `board.js sync`/`render` CLI writes refuse on an initialized journal;
bootstrap/release construction without a journal retains the raw renderer.


Standalone `gov log-question` and the regeneration performed by `gov sync` run
inside journaled mutations. Sync commits the question log alongside generated
artifacts only after provenance checks pass. Neither PLAN.md nor QUESTIONS.md
is exempt from detection of unjournaled semantic edits.

`gov reconcile --reason "<why>"` alone may reconcile recoverable runtime
lock/session drift. Accepting other governed-file drift or establishing a
missing baseline requires `--human-admin-override "<approval for exact changes>"`.
The approval statement and accepted paths are recorded in the journal. The
statement is an explicit operator attestation under the existing human-admin
model; it is not cryptographic proof of the speaker's role. Agents must obtain
that approval, not invent it. `--dry-run` reports whether approval is required
without accepting any drift.

### Drift scopes and committed authored content (ADR 0020)

Every drift detector (the journal seal, the git-status tree guard and `gov
doctor`) reports each changed path in exactly one scope, using
`coord/engine/scripts/drift-scope.js`:

- `engine`: the engine-managed surface. Restore the file, or after an
  intentional engine change re-pin with `gov verify-engine --pin`. Reconcile
  never adopts engine drift.
- `governed`: project-owned authority and authored content (board, plan records,
  prompts, decisions, QUESTIONS, docs, and project files outside `coord/`).
- `derived`: rebuildable views (rendered tables, PLAN.md, context packs). Use
  `gov sync` to regenerate them.
- `runtime`: sessions, locks, threads and other local runtime state. Use
  `gov recover`, or `gov reconcile --reason`.

The verdicts say whether the engine is intact and count project paths
separately, for example "engine intact, 403 project paths uncommitted".
`gov reconcile --scope <governed|derived|runtime>` adopts only that scope and
leaves drift in the other scopes detectable. The approval rules above still
apply.

Committed-state policy (human-admin decision 2026-10-24, ADR 0020): tracked
content committed at HEAD counts as reconciled ONLY for authored-content classes
(prompts and decisions/ADRs). Adoption runs at the start of a governed mutation,
in the canonical integration tree only. HEAD must be reachable from the
integration branch, and from `origin/<branch>` when that ref exists. The file
must match HEAD exactly, with no staged, unstaged or untracked difference.
Every adoption appends a `journal-baseline` event with
`details.reason = "committed-state-adoption"`, the commit sha, and the adopted
paths. The board, plan records, PLAN.md and QUESTIONS.md stay journal-only:
committing them does not reconcile them, and the seal still fails closed on
them.

Global plan regeneration must refuse before replacing artifacts if it would
remove an already-materialized section for a doing or review ticket. This does
not widen ticket-scoped schema validation to unrelated records.

## 10.9) Live-MCP Lifecycle Enforcement

A ticket that performs a live/production MCP operation declares it EXPLICITLY by recording a structured `live_mcp` object on its plan record:

```bash
coord/scripts/gov update-plan <ticket> --live-mcp '{"adapter":"<adapter>","operation":"<op>","operation_class":"read_sensitive","environment":"prod","scope":"<explicit scope>","redaction":"masked","approval":"human-admin","receipt_path":"coord/evidence/live-mcp/<receipt>.json"}'
```

The presence of `live_mcp` (and ONLY its presence — never a description keyword match) turns on the live-MCP lifecycle enforcement gate in `coord/engine/scripts/live-mcp-lifecycle.js`. For a declared live-mcp ticket, move-review / closeout readiness BLOCKS until the required evidence is present:

- operation class, adapter, operation, environment, and explicit scope;
- redaction evidence when the operation class requires it (`read_sensitive`, `write_prod`, `destructive`);
- approval evidence when the operation class requires it (any class above `read_safe`);
- cleanup completion when the class policy requires it, or when `cleanup_required=true` is declared;
- a recorded receipt — either embedded (`live_mcp.receipt`, validated with the COORD-152 receipt verifier) or referenced by path (`live_mcp.receipt_path`);
- fixture/test/spec promotion evidence (`live_mcp.promotion`) when `product_impact=true`.

The operation-class policy (which classes require approval/redaction/cleanup) is sourced from `OPERATION_CLASSES` in `coord/engine/scripts/runtime-evidence.js`; this module does not re-derive it. Governance core governs intent and evidence only — it never calls a production tool. The gate is DEFAULT-OFF: a ticket with no `live_mcp` declaration carries no new requirements and is completely unaffected. `gov explain` surfaces the same missing-evidence list under `live_mcp_lifecycle`.

## 11.0) Integration Authority (COORD-915, ADR 0021)

Three permissions are distinct, and holding one never implies another:

1. **Register an identity** (`gov agentid`, `gov agent-claim`): attribution only.
2. **Own a ticket attempt**: the existing ticket lock and owner lease; the owner works in its assigned worktree.
3. **Integrate canonical state**: board publication, canonical commits, `gov sync` (with or without `--commit`/`--push`), the terminal verbs (`land`, `finalize`, `close`, `finish`, `mark-done`, `finish-ticket`, including their post-finalize sync and push), `supersede`, `reconcile`, `reconcile-landings`, `pr-merge`, `rebuild-board`, `repair-chain`, `migrate-chain-hash`, `backfill-plan-records`, `retire-stale-drift-notes`, and `audit-landings --write`.

**Domain.** A coordination domain is one canonical runtime directory (`coord/.runtime`). Its integration-authority record is `coord/.runtime/integration-authority.json`. Ownership follows the domain and the workspace accessed, never where an agent runs: an SSH session into the canonical checkout is another writer in the same domain. An independent clone with its own runtime is an independent domain.

**Holder.** Each domain has at most one holder, named by handle and session, with when and how it was granted. In a domain that has never had a holder, the first attributed session whose publication verb (`sync`, a terminal verb, `supersede` or `pr-merge`) changes canonical state becomes the holder (`granted_via: implicit-first-integration-verb`), so a single-orchestrator workflow needs no extra command. `sync` journals its grant (or holder-session refresh) before it publishes, so the same `sync --commit` commits that event and the journal never lags HEAD. The other publication verbs grant only after they change canonical state. `gov integration claim` establishes the holder explicitly; after `gov integration release` the domain has no holder and the next one must claim explicitly. Any other session's integration verb is refused, naming the holder and the handoff verb. A session that was never bound to an identity cannot integrate once a holder exists. Handoff is explicit and journaled: `gov integration handoff --to <handle> --human-admin-override "<reason>"`.

**Operation reservation.** An integration operation (merge, record evidence, finalize, publish) holds the authority from start to end. A terminal verb opens an operation record (ticket, verb, step, start time, executor pid and host, lease expiry, baseline HEAD and journal size) before its first side effect and closes it after its publication step. `gov integration begin <ticket>` opens one earlier, for example before an externally merged PR, and the terminal verb for that ticket adopts and closes it. While an operation is open, every dispatched governed write by another session in the domain is refused (every router verb is classified in `coord/engine/scripts/integration-authority.js`, and a test fails when a verb is unclassified), and `withGovernanceMutation` refuses the same writes inside the runtime lock. Identity-only verbs stay allowed.

**Journal and atomicity.** Every authority event is a governed transaction in the hash-chained journal (`coord/.runtime/governance-events.ndjson`), in addition to the record's own history. The events cover:
- a grant (`integration-grant`, with `granted_via: implicit-first-integration-verb`, or `integration-claim`);
- a holder-session refresh, a handoff (naming both handles and sessions), a release;
- `integration begin`, and a terminal verb's operation close or interruption;
- each recovery.

A terminal verb's own reservation is a lock-only runtime write. Its authority events (an implicit first grant held provisionally inside the operation, a holder-session refresh, the close or interruption) are journaled only when the verb changed canonical state, meaning the journal grew or canonical HEAD moved. A refused or no-op terminal verb restores the record and appends nothing, so the COORD-843/855 contract holds: a refused closeout leaves the journal byte-identical. A provisional grant is usable only by its live operation. After a crash it confers no authority, the operation stays recorded, and the domain needs an explicit `claim` and then `recover`.

Each event names the handle, session, `granted_via` or command, and a transaction id. The record and its event commit as a pair: the record carries a `pending` mark naming the transaction until the event is appended. Any later read that finds the mark completes the pair if the event exists, and otherwise restores the prior record. So authority is never usable without its journal event, and a retry converges to exactly one grant and one event. `gov integration status` shows the holder and the journaled grant event's timestamp.

**Bootstrap after upgrade.** Keep competing governed writers paused from upgrade activation until the claim is recorded. Then:
1. Run `gov integration claim` as the intended orchestrator.
2. Run `gov integration status` and confirm the recorded holder and its grant event.
3. Reopen access.

Concurrent first claims are serialized by the runtime lock. Exactly one session wins, the loser is refused naming the winner, and the journal holds one grant event.

**Interruption and recovery.** A terminal verb that fails after a side effect (journal growth or a moved canonical HEAD) leaves its operation recorded as interrupted; one that fails before any side effect clears it. A crashed executor, an expired lease, an interruption, or a handoff all leave the operation recorded, and every integration verb is refused until `gov integration recover` verifies it (ticket status, executor liveness, journal growth, HEAD movement, dirty canonical paths) and the holder resumes it (`--resume`) or a human admin abandons it (`--abandon --human-admin-override "<reason>"`). Expiry or a gone executor never authorizes another session: a change of executor is always `integration handoff` with `--human-admin-override`, then verified `integration recover`. A live executor on this host cannot be resumed or abandoned; an executor on another host needs `--human-admin-override`. Outside the configured transition window, that requires signed approval for `integration recover --resume` or `integration recover --abandon`; during the window only the existing abandon exception applies. Resume is never a transition-window verb. The signer deployment must explicitly allowlist each verb; adding a test fixture does not enroll a production signer.

**Not yet protected (first version).** These limits are deliberate and must not be read as complete protection:
- The guard runs at the CLI and MCP dispatch boundary and inside `withGovernanceMutation`. Code that writes canonical files or runs `git commit`/`git push` without either (a hand-run `git` command, an external script, or a module called directly) is not refused by this mechanism; the existing pre-bash guard and journal seal still apply.
- Before any holder exists, a session with no attributed identity can still run integration verbs without becoming the holder (the pre-915 behaviour for unattributed callers).
- Repair verbs (`reconcile`, `reconcile-landings`, `repair-chain`, `migrate-chain-hash`, `backfill-plan-records`, `retire-stale-drift-notes`, `audit-landings --write`) require the holder once one exists. In a domain that has never had a holder they run without granting, because their journal contracts (COORD-715/722/835/836) admit no extra event.
- The first identified session to publish in an empty domain becomes the holder. Run `gov integration claim` as the intended orchestrator immediately after upgrading.
- Identity is the handle bound to the runtime thread. A session that rebinds itself to the holder's handle (`gov agentid --owner <holder>`) is treated as the holder; impersonation is governed by the identity rules in Section 10.3, not by this record.
- Independent runtimes on separate hosts or clones are separate coordination domains, and this record does not coordinate between them. Merging one domain's work into canonical goes through the canonical domain's holder. An SSH session that executes against the same canonical checkout is not in this category: it shares the canonical runtime and is refused as a competing writer in the same domain (the COORD-888 incident shape, covered by the incident test).
- An operation whose executor process ran on another machine that reached the same runtime (for example over a network mount) cannot have its liveness checked. It counts as live until a human admin passes `--human-admin-override` to `recover`.
- `doctor --fix`, `orch --fix`, `verify-engine --pin`, `gate` and other writes are reserved against an open operation but do not require integration authority.

## 11) Orchestrator Contract

The orchestrator is a governed operator role, not an implied convention.

Responsibilities each cycle:
- assign or recommend next tickets
- report each owner's unrelated `doing` tickets (no closeout-blocker exception links them) as a doctor `owner-doing` warning; the per-owner refusal (`wip-cap`) is retired (ADR 0021, COORD-963)
- detect stale, malformed, missing, or future-dated locks
- triage unresolved items addressed to `orchestrator` in `coord/QUESTIONS.md`
- detect blocked tickets that exceeded the board's configured staleness threshold
- keep canonical board state, governed locks, and passive alert queues coherent before making new assignment decisions

Required command:

```bash
coord/scripts/gov orch
```

Cycle rules:
- run `coord/scripts/gov orch` before and after any meaningful orchestrator assignment or reconciliation batch
- `coord/scripts/gov orch --fix` may apply deterministic local repairs, but must leave foreign ticket cleanup report-only
- there is no batch foreign-cleanup verb. Foreign-touch recovery is per ticket and needs a human-admin override: `coord/scripts/gov lock-abandon <ticket-id> --human-admin-override "<reason>"` for a stale lock, or `coord/scripts/gov claim <ticket-id> --transfer-to <handle> --human-admin-override "<reason>"` for an ownership transfer
- do not assign additional work while `coord/scripts/gov orch` is failing hard checks

Hard checks enforced by the orchestrator cycle:
- board validation passes
- governance doctor passes
- each `doing` ticket has a valid governed lock with a canonical worktree path
- no lock heartbeat is more than 5 minutes in the future
- no active `doing` lock heartbeat is stale by more than 24 hours
- canonical code-repo roots are not left dirty outside governed worktrees

Passive alerts that must be triaged in the same cycle:
- unresolved `coord/QUESTIONS.md` rows where `To = orchestrator` and `Resolved != yes`
- `doing (blocked: ...)` tickets older than 90 minutes based on lock `started_at_utc`
- repeated governance-drift notes that have not been reconciled into a resolved question or a governed repair action
- stale or unknown foreign worktree residue; report it by default and use explicit cleanup mode only when a human-admin authorizes batch cleanup
- an owner holding unrelated `doing` tickets (`[owner-doing]` doctor warning): finish or reassign one, or record a closeout-blocker relation if the pair closes together. This is attention, not state: locks, declared commit scope, the integration-authority guard and dependency readiness cover the state risks (retirement review, integration authority claudea11, COORD-915 holder, 2026-11-14; human-admin approved in session)
- total concurrent `doing` tickets is reported for review; there is no hard total limit (the former 5-ticket WIP limit was documented, not engine-enforced)

Cycle close criteria:
- either the hard checks pass, or the orchestrator records why a human-admin waiver is required
- unresolved passive alerts are either answered, reassigned, split into follow-up tickets, or explicitly left as acknowledged debt in `coord/QUESTIONS.md`
- if stale or conflicting ownership is found, resolve it in the same cycle with `resume`, `recover`, `reconcile`, reassignment, or legal status repair

## 11.1) Safety Properties

This section documents the enforcement mechanisms that underpin the governance model.

### Lock Atomicity

Governance locks use POSIX `mkdir` for acquisition, which is atomic at the OS level. Two agents cannot simultaneously acquire the same lock. If a process crashes after acquiring a lock but before releasing it, the lock is reclaimed automatically after staleness thresholds are exceeded (24 hours for ticket locks, 2 minutes for runtime locks).

### Journal Integrity

The governance event journal (`coord/.runtime/governance-events.ndjson`) is append-only. The system uses it to detect board regression (e.g., a bad merge rolling back ticket statuses). Behavior on journal state:
- **Missing journal**: treated as uninitialized; auto-bootstrapped on first governed mutation
- **Corrupt entry**: fails closed — the governance CLI refuses to proceed until the corruption is resolved
- **Deleted journal**: regression detection is lost, but all other governance mechanisms continue to function

If the journal is lost, run `coord/scripts/gov doctor` to assess state, then manually re-establish a baseline with the next governed mutation.

#### Tamper-evidence (hash-chain)

The journal is a tamper-evident hash-chain (ENT-002, Community-tier, repo-local). Each appended event records `prev_event_hash` — the canonical hash of the immediately-preceding stored event — so any reorder, in-place tamper, or dropped event breaks a chain link and is detectable:
- **`gov doctor`** verifies chain integrity board-wide and reports a broken link as an error.
- **`gov conform`** is a read-only verb that verifies the chain end-to-end and prints the chain head plus a pass/fail verdict. This is the local self-verify; the chain head is the attestation input a future central re-hash service would re-compute. Run `coord/scripts/gov conform` (add `--json` for machine output) anytime; it never mutates governed state.
- **`gov verify-engine`** (ENT-011, Community per-team) pins the engine surface to a known-good version and detects drift from it WITHOUT signing (signing is the Enterprise half, ENT-008). `coord/scripts/gov verify-engine --pin` snapshots the current surface (the `TEMPLATE_SYNC_MANIFEST` version + its sha256 fingerprint, reusing ENT-010's conformance fingerprint, plus per-file checksums and POSIX permission modes where supported) into `coord/engine-pin.json` — the only mutation. Windows omits POSIX mode enforcement. `coord/scripts/gov verify-engine` (no flag, add `--json`) is read-only and reports IN-SYNC or DRIFTED with the offending file paths. This is complementary to `check-template-sync`: that verifies internal manifest-vs-files consistency, while `verify-engine` verifies drift from a frozen pinned version (re-pin after an intentional engine bump).
- **Migration is non-destructive**: events predating the chain (legacy, written before ENT-002) carry no `prev_event_hash`; they validate as accepted-but-unverified "pre-chain" events rather than false tamper alarms. The first chained append on a legacy log writes an explicit, auditable `chain-anchor` event so history is never rewritten.
- **Torn-tail repair re-anchors explicitly**: a crash-truncated tail (COORD-033) is re-anchored by the auditable `journal-tail-repair` marker, so a legitimately repaired tail does not read as tamper.

### Feature Proof Verification

Feature proof entries (`path:`, `symbol:`, `text:`, `route:`) are validated at two levels:
- **Format validation** at plan-entry time (regex checks)
- **Existence verification** at landing time via `git cat-file`, `git show`, and `git grep` against the canonical branch

This means an agent can record a proof entry during development, but the entry is verified against the actual codebase before the ticket can land.

### Lock Release Guarantees

All governance mutations that acquire locks use `try/finally` blocks. If a subprocess fails (e.g., `git` or `gh` command error), the lock is still released. The governance CLI never leaves a lock held after an error.

### Doctor Repair Scope

`coord/scripts/gov doctor --fix` applies only deterministic, non-destructive repairs:
- creates missing plan stubs for `doing`/`review` tickets
- when invoked as `coord/scripts/gov doctor --fix --ticket <ticket-id>`, rebuilds mirrored board owner/status and session binding from a complete non-stale canonical doing lock for that ticket
- removes locks for tickets not in `doing` status
- reclaims stale locks (24h+ inactive)
- removes orphaned coord worktrees verified as abandoned

Outside that ticket-scoped canonical-lock rebuild path, it does not modify board ticket data, rewrite plan records, or alter governance event history.

### Limitations

The governance framework enforces the **structure** of coordination (statuses, locks, evidence, review cycles) but has inherent limitations:
- **Self-review quality**: the framework validates that review cycles exist and have required fields, but cannot verify the depth or correctness of the review content
- **Cross-repo atomicity**: if a cross-repo change lands in one repo but fails in another, there is no automated rollback; the failed portion must be handled as a new ticket
- **Orchestrator liveness**: if no agent runs `coord/scripts/gov orch`, stale locks and blocked tickets will accumulate without alert; the preflight script detects this and warns when the last orchestrator cycle is older than 24 hours
